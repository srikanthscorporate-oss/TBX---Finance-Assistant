🎯 Design Paradigm

Sequential-with-Parallel-Sub-Steps Agent Orchestration

Each user request flows through agents in strict order: Router → Scope Guard → Query Planner → Execution. Within a plan, queries may execute in parallel where independent. Request context persists via session state (Redis). Per-session serialization prevents race conditions; cross-session parallelism maximizes throughput.

📋 Architectural Decisions (ADs)

AD-1: Agent Orchestration Paradigm — Sequential-with-Parallel-Sub-Steps
Binds
Router initiates; Scope Guard validates scope; Query Planner generates execution plan; Execution Agent runs queries sequentially or in parallel per plan.
Prevents
Circular agent dependencies, deadlocks, out-of-order execution.
⚠️ ASSUMPTION: Orchestration is synchronous per request; no long-lived agent workflows across sessions.
AD-2: State Management — Session-Based Context Carriage
Binds
Each user conversation maintains session state in Redis (fast access, TTL-managed); query history + agent outputs cached for session context window.
Prevents
State loss across agent transitions, duplicate query execution, context bloat.
⚠️ ASSUMPTION: Session TTL = 4 hours; stale sessions evicted automatically.
AD-3: Router Responsibility — Intent Classification + Model Selection
Binds
Router parses user intent (financial query classification), selects primary model (Groq) vs advanced (RunPod for complex analysis), routes to appropriate Scope Guard.
Prevents
Model waste, out-of-scope queries bypassing guardrails, intent misclassification.
⚠️ ASSUMPTION: Intent classification uses prompt-based routing (no separate ML classifier); model selection is deterministic per query type.
AD-4: Scope Guard — In/Out-of-Scope Validation
Binds
Binary gate before Query Planner; validates query against domain (spend, payouts, reconciliation only); blocks out-of-scope with clear user message.
Prevents
Unauthorized data access, compliance violations, LLM jailbreaks.
⚠️ ASSUMPTION: Scope decisions are static rules (no learned guardrails); violations logged for audit.
AD-5: Query Planner — Execution Plan Generation (DAG-like)
Binds
Generates query plan as structured steps (which ClickHouse queries, in what order, dependencies); async-capable but sequential by default.
Prevents
Redundant query execution, missing joins, incorrect data ordering.
⚠️ ASSUMPTION: Plans are deterministic per query type; no dynamic replanning mid-execution.
AD-6: Execution Agent — Transactional Query Runner
Binds
Runs plan steps against ClickHouse; validates each result; aggregates for final response. Error handling: retry once per query, fail-fast on validation error.
Prevents
Partial data returns, corrupted aggregations.
⚠️ ASSUMPTION: ClickHouse is the single source of truth; PostgreSQL is transactional backup (not used for analytics queries).
AD-7: Data Contract — JSON Request/Response Envelope
Binds
All agent-to-agent communication via typed JSON envelopes (AgentRequest, AgentResponse, QueryPlan, ExecutionResult).
Prevents
Type mismatches, lost metadata, untraced agent calls.
⚠️ ASSUMPTION: Envelopes versioned; schema drift caught at deserialization.
AD-8: Error Handling — Per-Agent Retry + Graceful Degradation
Binds
Router/Scope Guard errors → user-facing error message; Query Planner errors → replan or escalate; Execution errors → retry once, then fallback response.
Prevents
Cascading failures, infinite loops.
⚠️ ASSUMPTION: Retry logic is stateless; no cross-request state pollution.
AD-9: Observability — Langfuse Tracing per Request
Binds
Each request traced end-to-end (entry point → Router → Scope Guard → Query Planner → Execution → Response); each agent transition logged with inputs/outputs.
Prevents
Blind spots in orchestration flow, hard-to-debug distributed issues.
⚠️ ASSUMPTION: Tracing overhead < 5%; async logging doesn't block request.
AD-10: Concurrency — Per-Session Serialization, Cross-Session Parallelism
Binds
One request per session at a time (avoid race conditions in session state); multiple sessions run in parallel.
Prevents
State corruption, race conditions, session conflicts.
⚠️ ASSUMPTION: Request-level locking in Redis; timeout = 30s per agent step.

🔄 Agent Orchestration Flow

User Request
    ↓
[Router Agent]
  • Parse user intent
  • Classify query type (spend analysis, payout reconciliation, etc.)
  • Select model (Groq for speed, RunPod for complex)
  • Log request_id, session_id
    ↓
[Scope Guard Agent]
  • Validate in-scope (spend, payouts, reconciliation, vendor lookup)
  • Check user permissions
  • Reject or pass to planner
  • Log compliance check
    ↓
[Query Planner Agent]
  • Analyze query intent
  • Generate execution plan (DAG of ClickHouse queries)
  • Annotate dependencies (seq or parallel)
  • Optimize for cost/latency
  • Validate plan structure
    ↓
[Execution Agent]
  • Execute plan steps (respect dependencies)
  • Validate each query result (schema, data types)
  • Aggregate results
  • Handle errors (retry once, then fallback)
    ↓
[Response Agent]
  • Format answer with evidence
  • Add citations & data lineage
  • Stream to user
  • Log final response

💾 Session State Architecture

Session (Redis)
├── session_id                    (UUID)
├── user_id                        (string)
├── created_at / ttl              (timestamp, 4 hours)
├── request_history
│   └── [req_1, req_2, ...]       (last N requests for context)
├── context_window
│   └── [agent_output_1, ...]     (last N agent outputs for LLM context)
├── agent_state
│   ├── router_classification     (cached intent)
│   ├── scope_validation          (passed / failed)
│   └── query_plan                (current/cached plan)
└── active_lock
    └── request_id, timestamp     (prevents concurrent modifications)

⚠️ Error Handling Strategy

Error at Agent X?
  ├─ Router error?
  │   └─ → User-facing: "I couldn't understand that. Try rephrasing."
  │
  ├─ Scope Guard error?
  │   └─ → "That query is outside my scope. I can help with: spend, payouts, reconciliation, vendor lookup."
  │
  ├─ Planner error?
  │   ├─ Can replan? → Retry with simplified plan
  │   └─ Cannot replan? → Escalate to Response Agent (fallback)
  │
  ├─ Execution error?
  │   ├─ Transient (timeout, connection)? → Retry once
  │   │   ├─ Success? → Continue
  │   │   └─ Fail? → Fallback response
  │   └─ Permanent (validation error)? → Fail-fast, escalate
  │
  └─ Response error?
      └─ → Log + generic: "I encountered an issue. Please try again."

📊 System Context for Designers

🚀 Scaling Model

  • Per-session serialization → No race conditions within a user's workflow
  • Cross-session parallelism → Handle 100 concurrent users efficiently
  • Redis session store → O(1) read/write per agent step; TTL auto-cleanup
  • ClickHouse queries → Handle 10k transactions/day; target P95 < 500ms per query
  • Model routing → Groq for speed (majority queries), RunPod for complex (tail queries)

🔐 State Consistency Guarantees

  • Session envelope is the single source of truth for in-flight request state
  • Agents are stateless; no direct inter-agent communication (all via session envelope)
  • Session lock (Redis) prevents concurrent modifications on same session
  • Lock timeout = 30s per agent step (fail-fast if exceeded)

🔍 Observability & Monitoring

  • Langfuse traces every request end-to-end (user → Router → ... → Response)
  • Each agent logs: inputs, outputs, latency, errors
  • Errors include full context: request_id, session_id, user_id, agent, step
  • Metrics tracked: latency per agent, error rates, cache hit rates, model usage

📈 Performance Targets

  • P95 end-to-end latency: < 3 seconds (Router → Response)
  • Per-agent timeout: 30 seconds (fail-fast if exceeded)
  • Query latency (ClickHouse): P95 < 500ms
  • Tracing overhead: < 5% (async, non-blocking)
  • Cache hit rate target: > 60% for repeated queries within session

🤔 Open Questions (Deferred)

  • Dynamic plan adaptation: Should Query Planner replan mid-execution if a query fails?
  • Escalation path: For queries Execution Agent can't handle, should there be a human review queue?
  • Retry strategy: Failed queries — should we retry with a simpler plan or escalate immediately?

🛣️ Implementation Roadmap

Phase 1: Foundation

  1. Build Agent Infrastructure — Agent base class, orchestration engine, session manager
  2. Implement Router Agent — Intent classification logic, model selection rules
  3. Implement Scope Guard Agent — Domain policy rules, compliance validation

Phase 2: Data Layer

  1. Design Query Planner Algorithm — How to convert financial query → ClickHouse DAG
  2. Implement Execution Agent — Query execution, validation, result aggregation
  3. Build Response Agent — Answer formatting, citations, streaming

Phase 3: Production Ready

  1. Error Recovery — Implement retry policies, fallback strategies
  2. Observability — Langfuse integration, metrics collection, dashboards
  3. Load Testing — Verify 100 concurrent users, latency targets, cache efficiency
